# 批量分析-修复-验证工作模式

> v51.0: 用户偏好模式，适用所有修复类任务。

## 原则

所有修复类任务严格按 **分析全部 → 一次性全部修复 → 最终验证** 模式执行。

**禁止**逐个修复逐个验证。

## 流程

```
Phase 1: 全量分析
  ├── delegate_task 并行分析不同维度
  │   ├── 架构维度
  │   ├── UX/内容规范维度
  │   ├── 代码质量维度
  │   └── 稳定性维度
  └── 汇总优先级矩阵 (P0/P1/P2)

Phase 2: 一次性全部修复
  ├── P0 批次 → 系统级风险
  ├── P1 批次 → 中等风险
  └── P2 批次 → 建议优化
  每个批次: 并行修复 → 不验证

Phase 3: 最终验证
  ├── 全量 quality_score
  ├── wikilink 断裂检查
  └── 测试套件全量运行
```

## 为什么

1. **上下文效率**: 逐个修复需要反复读相同的文件 → 浪费 token
2. **依赖关系**: 修复 A 可能暴露 B 的问题 → 一次性看到全貌才能正确排优先级
3. **验证一致性**: 逐个验证可能发现修复 B 破坏了 A → 全量验证才能暴露交互问题

## 实战案例

| 项目 | 分析维度 | P0项 | P1项 | P2项 |
|:-----|:---------|:----:|:----:|:----:|
| domain-book-wiki 工程审计 | 代码质量/测试/架构/稳定性/工程化 | 5 | 4 | 7 |
| EMC知识库质量修复 | wikilink/公式/SP空壳/Scene Mermaid | 3 | 2 | 2 |

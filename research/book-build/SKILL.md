# book-build（教材写作管线）

## Overview

**大纲驱动，写作大纲供料，严格遵循结构，专业级学术写作。** 写作大纲是原料，教材是成品——不能把大纲结构复制到教材正文，必须重新组织为自然叙述的学术散文。

**专业教材 = 权威定义 + 直观引入 + 编号公式 + "式中"变量解释 + 含数字实例 + 层次化习题。**

**全自动执行（客户核心偏好）**：执行任务时**不问"要不要/是否继续"**，直接做。做错了再改也比停下来问效率高。只需在完成后汇报结果。

**P0与P1阶段策略差异**（2026-06-10 实战验证）：
- **P0（结构性缺失补充）**：缺失小节、军规检查占位、素材清单 → 直接 `patch` 插入少量框架内容即可，每章增加10-50行
- **P1（内容质量提升）**：真实案例、计算型例题、参考书盲区深度补充 → 必须用 `delegate_task` + 参考书源文提取，每章可能增加50-200行新内容
- 不要混淆：用P0的patch方式做P1会导致内容空洞、案例虚假。P1的每个案例需含具体技术细节（公司名、时间、参数值、工程分析）
- P1前应先运行 `outline_vs_chapter_audit.py` 生成 `补充执行清单.json`，按 P0→P1→P2 优先级执行

**P0 全量补充管道**（2026-06-12 实战验证，9章批量成功）：
```bash
# Step 1: 差距分析
python3 scripts/outline_vs_chapter_audit.py \
  --project /path/to/教材 --output /path/to/教材/output

# Step 2: 分析报告 → 确认缺失项
#   注意：大纲中的 5.1/5.2 节是写作说明/军规检查，不要写入教材正文
#   P0 仅包括：缺失内容节 + 缺失本章总结

# Step 3: delegate_task 并行执行补充
#   缺失内容节（每节独立任务，需创作）
#   缺失小结（3章一个任务）
#   公式汇总表（4章一个任务，但写完立即删除！见 ⚠️ 关键澄清）

# Step 4: 重跑公式编号
python3 scripts/batch_fix_formula_numbers.py /path/to/教材/output/第*.md

# Step 5: git 提交
cd /path/to/教材 && git add -A && git commit -m "feat: P0补充..."
git push
```
**关键经验**：
- 缺失内容节需要独立委托创作
- 新增内容节可能引入新公式，必须最后重跑 batch_fix
- `.gitignore` 需排除：`.DS_Store` `.idea/` `*.bak` `output/fix_*.py` `output/补充与完善分析报告.md` `output/补充执行清单.json`
- 审计输出（分析报告 + 执行清单）每次可重新生成，不要提交到 git

## 章节格式标准（2026-06-12 统一）

每章开头格式：

```markdown
# 第X章 章节名称

## 内容提要

本章概述段落。

通过本章学习，读者应达成以下学习目标：

1. 能......（不要加 Bloom 分层标签）
2. 能......
...
```

**禁止**：

- ❌ `**记忆层**`、`**理解层**` 等 Bloom 分类标签（2026-06-12 用户明确拒绝 "不要加上Boolm这种东西"）
- ❌ `## 学习目标` 标题（必须统一为 `## 内容提要`）
- ✅ 统一数字编号 `1. 2. 3. ...`

## 内容扩充工作流（2026-06-12 新增）

当用户指出某章节体量不足或需要扩展时，使用以下工作流：

### 触发条件
- 章节体量显著低于写作大纲中定义的"建议体量"目标（如大纲目标300KB，实际仅60KB）
- 用户明确要求扩充某章内容

### 执行步骤

```bash
# Step 1: 读取写作大纲，提取目标体量
#   写作大纲中的表格定义了每节建议KB数
#   例如 8.1.1 建议25KB, 8.1.2 建议25KB ...
#   将各节目标乘以当前完成比例得到实际目标

# Step 2: 读取当前章节，识别缺失子节
#   大纲定义了大量子节（如6.3.3~6.3.6、6.5等）可能完全缺失
#   用 delegate_task 并行扩充（每章一个独立任务）

# Step 3: delegate_task 指令模板
指令中包含：
- 当前文件路径和体量
- 写作大纲路径
- 大纲定义的子节列表（标注哪些缺失）
- 目标体量（如"至少扩充至150KB"）
- 每个子节需含的计算公式和工程实例
- ⚠️ 公式编号需保持连续：用 \\\\tag{章-XX}
- ⚠️ 最后运行 batch_fix_formula_numbers.py 修复编号

# Step 4: 批量修复公式
python3 scripts/batch_fix_formula_numbers.py /path/to/教材/output/第*.md

# Step 5: git 提交
```

### 关键经验
- **并行度控制**：每个章节用独立 delegate_task，但 max_concurrent_children=3
- **公式连续性**：subagent 必须知道当前章节已有多少公式（用 `grep -c '\\\\\\\\tag{章-'` 快速统计）
- **batch_fix 是必要步骤**：分发写作时公式编号可能冲突或跳跃
- **不删除已有内容**：只在各节内/节后补充，不替换已有内容
- **优先补充大纲定义的子节**：大纲列出的子节就是用户期望的内容树
- **subagent timeout**（600s）：如果章节扩充量很大（+50KB以上），分多次委托，每次只扩充2-3节

### 与 P0 的区别
| 维度 | P0（结构性补充） | 内容扩充工作流 |
|:----|:---------------|:--------------|
| 触发条件 | 缺失小节/小结 | 章节体量不足 |
| 补充量 | 每章10-50行 | 每章数百至数千行 |
| 目标 | 补全结构骨架 | 达到大纲目标体量 |
| 方法 | 直接 patch | delegate_task 并行创作 |
| 公式编号 | 批次统一修复 | 需关注连续性 |

**⚠️ 关键澄清：写作说明/军规检查/公式总结不是教材正文**

本章写作说明、12条军规落实检查、全章核心公式总结是**写作过程中的质量检查工具**，供 agent 在内部使用，**不得写入教材成品**。教材正文只应包含：

- 叙述性章节内容（定义、原理、推导、分析）
- 编号公式（`\tag{章-序号}` 格式）
- 表格、Mermaid 图、图片
- 例题与习题
- 参考文献与深入阅读

**不要**在教材正文中添加：
- `## X.Y 本章写作说明`（含素材来源清单）
- `## X.Y.Z 12条军规落实检查`
- `## ★ 全章核心公式总结`（公式已在正文中用 `\tag{}` 编号）

如果需要记录写作说明用于质量追溯，使用项目根目录下的独立文档记录，不要污染教材正文。

**案例真实性铁律**：教材中的案例**必须来自真实事件**（公开报道/工程记录/标准测试数据），不得从参考教材（路宏敏/张亮/梁振光/柯金良等）直接摘抄。替换案例时，改用丰田EMI事件、iPhone 12 SAR超标、5G C-band干扰、波音787电池EMC等公开真实事件。

**公式格式铁律**（写作阶段必须执行）：
- `\\tag{N-M}` **独占一行**，紧跟在公式内容之后、**闭合 `$$` 之前**（即 `$$` 闭合行的前一行），禁止与公式同行或放在 `$$` 之前
- 正确格式：
  ```
  $$
  公式内容
  \\tag{N-M}
  $$
  ```
- 错误格式（会导致配对错位）：
  ```
  $$
  公式内容
  $$
  \\tag{N-M}   ← 错误！tag 在 $$ 之后
  ```
- `$$` **独立一行**，禁止公式内容与 `$$` 写在同一行
- 行内公式用单 `$` 包裹：`$E=mc^2$`
- 引用块内公式使用 `> $$` 而非 `$$`，内容行用 `>` 前缀，`\tag{}` 也需加 `> ` 前缀：
  ```markdown
  > **柯金良观点：**
  >
  > $$
  > 公式内容
  > \tag{N-M}
  > $$
  >
  > 后续正文
  ```
- 违反以上规则 → 运行 `batch_fix_formula_numbers.py`（v3+）自动修复

**公式编号系统性缺失的根因与修复（2026-06-11 诊断确认）**：
- **根因**：AI Agent 在写作阶段系统性忽略 `gen_prompt.py` 中"公式编号：`\tag{章-序号}`"指令，739个公式100%无编号
- **这不是 post_generation_check 的 bug**：`check_formulas` 只报告不删除；`_fix_missing_tag` 只补缺但不做全局重编号
- **正确修复路径**：对整章运行 `python3 scripts/batch_fix_formula_numbers.py output/第N章-*.md`（v3 blockquote 安全版：保留 `> $$` 结构，状态机同时识别 `$$` 和 `> $$` 为边界）。对于无格式问题的简单文件也可以用 `python3 scripts/renumber.py output/第N章-*.md`，但 batch_fix_formula_numbers.py 更安全（同时覆盖 blockquote 公式/未闭合 $$/空块三类潜在问题）。
- **预防**：在 `delegate_task` 写节的 context 中必须显式包含"每个 $$ 公式块必须紧跟 \tag{章-序号} 编号"的强约束
- **验证**：修复后运行 `python3 scripts/post_generation_check.py output/第N章.md --fix` 确认所有公式块都有编号
- **批量修复工具**：使用 `scripts/batch_fix_formula_numbers.py`（v3 blockquote 安全版：保留 `> $$` 结构，状态机同时识别 `$$` 和 `> $$` 为边界，空块清理，未闭合 `$$` 修复，自动加 blockquote 标签前缀；安全版：先读后写+自动备份）；对复杂的三重复合故障（`>$$` + 未闭合 `$$` + tag 位置错误同时出现），运行一次即可修复全部问题。**必须使用 v3+，v2 会破坏 blockquote 公式**。

## 关键陷阱（2026-06-11 实战新增）

### 陷阱 A：正则 `\$\$(.*?)\$\$` 匹配不可靠
- **不能用** `re.findall(r'\$\$(.*?)\$\$', content, re.DOTALL)` 进行公式块匹配——当公式内容包含 `{` 或 `}` 字符时可能产生错误配对；且当引用块内存在 `>$$` 时正则根本不会匹配（因为 `>$$` 不是 `$$`）
- **必须用行级状态机**：逐行扫描 `$$` 行（或 `>$$`/`> $$` 规范化后的 `$$`），用布尔标志 `in_formula` 配对
- **行级状态机模板**：
```python
in_formula = False
for line in lines:
    if line.strip() == '$$':
        in_formula = not in_formula
    # 在 in_formula 状态切换时处理公式块
```
- **完整修复流程**（含 `>$$` 处理和未闭合 `$$` 检测）：见 `references/formula-numbering-diagnosis.md` 陷阱 D2-D3

### 陷阱 B：空 `$$...$$` 块导致编号偏移
- 现象：`$$\n\n$$`（内容为空或只有空行）被当做一个公式块跳过，导致后续所有编号 +1
- 修复：编号前先扫描并删除所有空 `$$...$$` 块

### 陷阱 C：孤立 `$$` 或 `> $$` 行破坏配对计数
- 现象：文件中存在前后都是空行或引用标记的独立 `$$`（或 `> $$`），不属于任何配对
- 修复：用状态机配对后（同时识别 `$$` 和 `> $$` 作为边界），收集未配对的边界行索引并删除，然后再编号

### 陷阱 D：`>$$` 引用块格式（v3 安全处理）
- **现象**：引用块内公式使用 `>$$` 或 `> $$` 而非 `$$` 作为边界
- **v2 错误做法**：将 `> $$` 替换为 `$$`（删除 `>` 前缀），删除空引用行 `>` → **这会破坏 blockquote 结构！**
- **v3 正确做法**：保留 `> $$` 不变，状态机同时识别 `$$` 和 `> $$` 为公式边界。插入 `\tag{}` 时自动加 `> ` 前缀
- **简而言之**：`> $$` 不是错误格式，它是 blockquote 中公式的正确写法

### 陷阱 D2：引用块公式修复导致配对错位（2026-06-11 新发现）
- **根因**：当文件中存在 `\tag{N-M}` 行紧跟在 `$$` 之前（格式错误：tag 应该在公式后、闭合 `$$` 前），且引用块内 `>$$` 被规范化为 `$$` 后，状态机会错误配对——`>$$` 变为 `$$` 后与后续未配对的 `$$` 形成巨大块
- **症状**：`$$` 总数为奇数（83 而非偶数），状态机配对中出现跨越 80+ 行的公式块（如 L872-L962），tag 位置验证大量失败
- **修复**：必须按以下顺序执行：
  1. 清除所有 `\tag{}` 行（不管位置是否正确）
  2. 规范化 `> $$` → `$$`
  3. 删除空引用行 `>`
  4. 删除连续 `$$`（空块）
  5. 用状态机配对，发现未配对 `$$` → 在公式内容后插入闭合 `$$`
  6. 再次删除连续 `$$`（修复后可能产生的）
  7. 行级配对 + 编号
- **绝对不要用**：先修复 `>$$` 再单独修复 tag 位置的补丁式方法——这会改变行号导致后续修复失效

### 陷阱 D3：`$$` 未闭合导致后续所有配对错位（2026-06-11 新发现）
- **根因**：原始恢复文件中某些公式块的 `$$` 没有闭合（如 L816 `$$` 开始但无闭合），状态机会一直往后找直到找到下一个 `$$`
- **症状**：出现 L872-L962 这样跨越 90 行的"公式块"，`$$` 总数为奇数
- **诊断**：配对后检查 `in_formula` 布尔值，如为 True 则存在未闭合 `$$`
- **修复**：在未闭合 `$$` 后的第一个非空行（公式内容）后插入闭合 `$$`

### 陷阱 E：批量处理脚本的致命错误模式
- **致命**：先 `open(fpath, 'w')` 打开写模式（清空文件），再 `open(fpath, 'r').read()` 读内容 → 读到空字符串
- **正确模式**：先 `open(fpath, 'r').read()` 保存内容到变量，处理后再 `open(fpath, 'w').write()`
- 所有批量修改脚本必须先做备份（`.bak`），再做验证（重读对比）
